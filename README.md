# Seidr

`Seidr` это vanity generator для Yggdrasil-адресов.

Он многопоточно перебирает Ed25519-ключи, вычисляет соответствующий Yggdrasil IPv6-адрес и ищет совпадения по заданному шаблону.

## Что

Программа строит такой pipeline:

```text
seed
-> ed25519 keypair
-> Yggdrasil IPv6 derive
-> match
-> вывод private/public key и адреса
```

Что умеет:

- искать по `hex`-префиксу
- искать по `IPv6 CIDR`
- искать по удобному `template`-формату
- работать в несколько потоков
- показывать `keys/sec`, время, число находок и шуточный счётчик `unluckiness`
- подбирать `batch` автоматически через `--batch auto`

Поддерживается и web-версия на Dioxus. Она лежит в папке `web/`, а этот README относится прежде всего к CLI.

## Зачем

Такая программа нужна, если хочется получить красивый или узнаваемый Yggdrasil-адрес. Например:

- адрес с удобным для чтения префиксом
- адрес с заданным фрагментом вроде `dead:beef`
- повторяемый шаблон для тестов, демо или личных экспериментов

Это не ускоритель сети и не магия для маршрутизации. Это просто инструмент перебора ключей, который помогает найти адрес нужного вида.

## Как

### Как это работает

На каждой итерации программа:

1. генерирует случайный Ed25519 seed
2. получает из него keypair
3. вычисляет Yggdrasil IPv6-адрес
4. проверяет адрес на совпадение
5. если совпало, печатает `private_key`, `public_key` и `address`

Важный момент: derive сделан так, чтобы совпадать с локальным `yggdrasil`, а не по упрощённой схеме "взять SHA512 и первые 16 байт". В проекте есть тесты, которые это проверяют.

### Как собрать

Обычная сборка CLI:

```bash
cargo build --release -p ygg-vanity
```

Запуск без установки:

```bash
cargo run --release -p ygg-vanity -- --template '200:?:?:?:dead:beef:?:?'
```

### Как искать адреса

По `hex`:

```bash
cargo run --release -p ygg-vanity -- --hex 02020fca
```

По `CIDR`:

```bash
cargo run --release -p ygg-vanity -- --cidr '202:fca::/32'
```

По `template`:

```bash
cargo run --release -p ygg-vanity -- --template '200:?:?:?:dead:beef:?:?'
```

У `template` есть важное правило:

- первый hextet считается декоративным и не участвует в матчинге
- `?` означает "любой hextet целиком"

То есть:

```text
200:200:200:?:?:?:?:?
```

означает поиск по 2-му и 3-му hextet, а первый нужен только для удобства записи.

### Как ускорять

Чаще всего полезны такие флаги:

```bash
cargo run --release -p ygg-vanity -- \
  --template '200:?:?:?:dead:beef:?:?' \
  --threads 8 \
  --batch auto \
  --batch-auto-secs 3
```

Что они делают:

- `--threads` задаёт число потоков
- `--batch N` вручную задаёт частоту сброса статистики
- `--batch auto` делает короткий autotune перед поиском и выбирает более удачный `batch`
- `--batch-auto-secs` задаёт длительность одного пробного прогона для autotune

### Что выводится в статистике

Пример:

```text
elapsed=4.0s keys=3342336 rate=851922/s overall=830288/s found=0 unlucky=0.08% exp≈4.295e9
```

Где:

- `elapsed` — сколько прошло времени
- `keys` — сколько ключей уже проверено
- `rate` — текущая скорость
- `overall` — средняя скорость с начала запуска
- `found` — сколько совпадений найдено
- `unlucky` — шуточная оценка "насколько уже обидно, что всё ещё пусто"
- `exp≈...` — ожидаемое число попыток для такого шаблона

### Как считается `unlucky`

`unlucky` это не "настоящая удача" и не строгая метрика качества поиска. Это просто удобная оценка того, насколько уже необычно, что при таком числе попыток ещё нет ни одного совпадения.

Считается так:

1. по шаблону определяется число фиксированных бит, то есть `fixed_bits`
2. вероятность успеха за одну попытку оценивается как `p = 2^(-fixed_bits)`
3. если сделано `N` попыток и пока найдено `0` совпадений, то

```text
unlucky = 1 - (1 - p)^N
```

В интерфейсе это выводится в процентах.

Интуитивно смысл такой:

- маленькое значение `unlucky` означает "ничего странного, просто ещё рано"
- большое значение `unlucky` означает "по идее уже могло бы повезти, а пока пусто"

Например, если шаблон имеет `fixed_bits = 32`, то среднее ожидание будет около `2^32` попыток, а `unlucky` будет постепенно расти по мере перебора.

Если хотя бы одно совпадение уже найдено, `unlucky` сбрасывается в `0%`, потому что ситуация "до сих пор ничего не найдено" уже больше не актуальна.

## Полезные замечания

- Чем больше фиксированных бит в шаблоне, тем дольше поиск.
- `template` обычно удобнее `hex`, если нужен красивый фрагмент в середине адреса.
- `--batch auto` немного задерживает старт, потому что сначала меряет производительность.
- Для очень редких шаблонов поиск может занимать долгое время. Это нормально.

## Пример результата

При нахождении совпадения программа печатает примерно это:

```text
match #1
private_key: ...
public_key: ...
address: 202:....
worker: 3
```
